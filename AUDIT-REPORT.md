# 🔎 Auditoria Cirúrgica — nixos-config (pré home-manager)

Revisão do estado atual do flake, **antes** da migração para home-manager.
Escopo: inconsistências, duplicidades e bugs reais — não é um redesign.
Nenhuma opção de comportamento foi alterada; apenas duplicações/bugs
corrigidos e documentação desatualizada realinhada com o que o código
realmente faz.

Todas as alterações estão neste zip, prontas para substituir os arquivos
originais 1:1 (mesma estrutura de diretórios).

## 🐛 Bugs reais (corrigidos)

### 1. `fileSystems."/".options` duplicado no `dell1564`
- **Onde:** `hosts/dell1564/hardware-configuration.nix` **e**
  `hosts/dell1564/default.nix` definiam `options = [ "noatime" "nodiratime"
  "commit=60" ]` para o mesmo `fileSystems."/"`.
- **Por que é bug, não só duplicidade cosmética:** opções do tipo lista no
  NixOS **concatenam** entre módulos em vez de sobrescrever. O sistema
  final ficaria com `options = ["noatime" "nodiratime" "commit=60"
  "noatime" "nodiratime" "commit=60"]` — mount options duplicadas de
  verdade na tabela de montagem.
- **Fix:** removida a redeclaração em `default.nix`; a fonte única de
  verdade continua em `hardware-configuration.nix`, ao lado de `device`/
  `fsType`.

### 2. SSH client config com hosts duplicados no próprio nome
- **Onde:** `configuration.nix`, no `system.activationScripts.setupBorbaSshKeys`.
- **O quê:** três blocos escritos como `Host gitea.com gitea.com`, `Host
  codeberg.org codeberg.org` e `Host codefloe.com codefloe.com` — o mesmo
  hostname repetido duas vezes na mesma diretiva `Host`, claramente um
  copy-paste bug (o padrão correto seria um único hostname, ou dois
  hostnames *diferentes* se a intenção fosse cobrir dois domínios).
- **Fix:** normalizado para um hostname por linha. Não é destrutivo — o
  `ssh_config` funcionava do mesmo jeito com o token duplicado — mas fica
  claro que o arquivo pretendia declarar hosts distintos e não o fez.
  **Se a intenção original era registrar um domínio adicional em alguma
  dessas linhas (ex. um segundo host além de `codefloe.com`), me diga qual
  e eu ajusto.**

### 3. `console.keyMap` / `services.xserver.xkb` duplicado no `mac2011`
- **Onde:** `hosts/mac2011/hardware-configuration.nix` **e**
  `hosts/mac2011/default.nix` definiam exatamente o mesmo layout de teclado
  (`us` / variante `mac`).
- **Detalhe extra:** o próprio cabeçalho do `hardware-configuration.nix`
  diz *"Do not modify this file! It was generated by 'nixos-generate-config'"*
  — mas alguém editou esse arquivo à mão para adicionar o bloco de teclado,
  quebrando a própria premissa do arquivo.
- **Fix:** removido o bloco duplicado de `hardware-configuration.nix`;
  `default.nix` continua sendo a fonte única e editável.

### 4. Pacote `swaylock` duplicado
- **Onde:** `configuration.nix`, `environment.systemPackages` — `swaylock`
  aparecia duas vezes na mesma lista.
- **Fix:** removida a segunda ocorrência. Efeito prático nulo (Nix
  deduplica o store path de qualquer forma), mas indicava descuido na
  lista que vale a pena manter limpa.

## 🧹 Duplicidade estrutural (arquivo órfão removido)

### 5. `devshells.nix` (raiz) — código morto, nunca foi wireado ao flake
- **Achado:** `flake.nix` **não importa** `devshells.nix` em lugar nenhum
  (`grep` confirmou zero referências). Além disso, `devshells.nix` espera
  os argumentos `nixpkgs-stable`, `fenix` e `flake-utils` — nenhum dos três
  é um input do `flake.nix` real (`flake.lock` só tem `nixpkgs`,
  `nixpkgs-unstable`, `sops-nix`). Ou seja: mesmo que alguém tentasse
  religar esse arquivo, ele quebraria a avaliação imediatamente.
- **Redundância:** o conteúdo de `devshells.nix` duplica quase 1:1 o que já
  existe (e funciona de fato) em `devshells/go/flake.nix`,
  `devshells/rust/flake.nix`, `devshells/lua/flake.nix`,
  `devshells/postgresql/flake.nix` e `devshells/mariadb/flake.nix` — o
  sistema real, documentado no `README.md` (`nix develop ./devshells/go`
  etc.), é o diretório `devshells/`, não o arquivo solto.
- **Fix:** arquivo removido. Nenhuma funcionalidade é perdida — ele nunca
  esteve ativo.

## 📝 Documentação desatualizada (realinhada com a realidade)

### 6. `README.md` — stack de desktop desatualizada
- Descrevia `Desktop: Niri & GNOME (Wayland via GDM)` para o mac2011 e
  `Desktop: i3 (X11)` para o Dell. **Nada disso existe hoje**: todos os 4
  hosts usam `niri` + `waybar` + `ly` como display manager (ver
  `configuration.nix`, seção "NIRI (Wayland) + LY"), não há GNOME/GDM nem
  i3/X11 em nenhum host.
- Também citava só 2 hosts (`mac2011`, `dell1564`); `macutm` e `macvmf`
  (as duas VMs Mac, com base compartilhada em
  `hosts/common/mac-vm-workstation.nix`) não apareciam na seção.
- **Fix:** seção "Supported Hardware" reescrita para refletir o stack
  real e os 4 hosts. Também sinalizei a inconsistência de nome
  `dell1564` (usado em todo o flake) vs. `Dell Inspiron 1456` (usado no
  README antigo e em `scripts/age-key-backup-e-restauracao.md`) — **não
  assumi qual é o correto**, só deixei a nota visível para você confirmar
  o modelo real do hardware.

### 7. `DENDRITIC-PATTERN.md` — descreve uma arquitetura que não existe
- O documento inteiro descreve `core.nix`, `profiles/minimal.nix`,
  `profiles/desktop.nix`, `modules/apps/default.nix` como agregador de
  opções, `hosts/dell.nix`, `hosts/macbook.nix` etc. — **nada disso existe
  no repositório real.** A árvore atual é: `flake.nix` →
  `configuration.nix` (monolítico) → `hosts/<host>/default.nix` (+
  `hosts/common/` só para as VMs Mac). Não há aggregators, não há
  `options.category.module.enable`, não há camada de `profiles/`.
- Isso é especialmente importante **agora**, porque no próximo passo
  (home-manager) seria fácil confundir esse documento com o estado real e
  tentar encaixar o home-manager numa estrutura de pastas que não existe.
- **Fix:** adicionei um banner explícito no topo marcando o arquivo como
  aspiracional/não implementado, sem apagar o conteúdo (pode ser útil como
  referência de design para uma refatoração futura, mas não deve guiar a
  migração do home-manager).

## ℹ️ Observações — não alterei, só sinalizo para sua decisão

Estes pontos **não** foram tocados porque envolvem uma decisão sua (dados
que não tenho, ou comportamento que pode ser intencional):

- **`.sops.yaml` ausente.** O `.gitignore` tem o comentário *"Note:
  .sops.yaml is NOT ignored — it contains only public keys and should be
  committed"*, mas o arquivo não existe em lugar nenhum do repo. Hoje isso
  não quebra nada porque `scripts/manage-ssh-sops.sh` sempre passa
  `--age <recipient>` explicitamente. Mas sem `.sops.yaml` você não tem um
  único lugar centralizando "qual age pubkey decifra qual host", o que vai
  doer se um dia quiser um segundo recipient (ex. uma chave de admin, além
  da chave de cada host) ou rodar `sops <arquivo>` interativo sem passar
  `--age` na mão. Não criei o arquivo porque precisaria das age pubkeys
  reais de cada host, que não estão no repo (só as versões cifradas).
- **`system.stateVersion = "26.05"` compartilhado globalmente** entre os 4
  hosts em `configuration.nix`. Isso só é seguro se todos os 4 hosts foram
  de fato instalados/ativados pela primeira vez sob essa mesma versão do
  NixOS — `stateVersion` não deveria ser "bumped" retroativamente em hosts
  mais antigos. Vale confirmar antes da fase 2, porque o home-manager tem
  seu **próprio** `home.stateVersion`, independente deste.
- **`pkgs-unstable` no `specialArgs`** é uma instância "crua" do
  `nixpkgs-unstable` (importada direto no `flake.nix`), não a `pkgs` que
  passa pelo module system. Hoje não há `nixpkgs.overlays` configurado em
  lugar nenhum, então não faz diferença — mas se você adicionar overlays
  no futuro (comum ao integrar home-manager com pacotes customizados),
  eles **não** vão se propagar automaticamente para `pkgs-unstable`; seria
  preciso aplicá-los also lá.
- **`environment.systemPackages` repetido em vários módulos**
  (`configuration.nix` global + cada `hosts/*/default.nix` +
  `hosts/common/mac-vm-workstation.nix`) é esperado e correto no NixOS —
  cada módulo contribui sua própria lista e elas concatenam. Não é bug,
  só deixo registrado que "duplicidade de pacote entre módulos diferentes"
  é normal e não precisa virar tarefa de limpeza.
- **`hardware.enableRedistributableFirmware = true`** é declarado
  separadamente em `hosts/dell1564/default.nix` e
  `hosts/mac2011/default.nix` (cada host Broadcom precisa dele). Dá pra
  extrair para um módulo `hosts/common/broadcom-wifi.nix` no futuro, mas
  não é duplicidade incorreta — é repetição de uma linha entre dois hosts
  com necessidade real e independente.
